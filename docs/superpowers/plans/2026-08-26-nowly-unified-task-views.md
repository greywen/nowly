# Nowly 统一任务与跨视图联动实施文档

日期：2026-08-26
状态：已确认，待实施
范围：看板、四象限、日历、任务、标签、协作人、模块设置与历史数据迁移

> 本文档是本次改造的最终产品与工程实施基线。它覆盖 `2026-08-12-kanban-module-design.md` 中“看板任务与四象限、日历相互独立”以及“看板自定义优先级”的旧结论；未被本文覆盖的看板泳道、拖放和视觉规范继续有效。

## 1. 结论摘要

本次改造不实现三套任务之间的复制或双向同步，而是建立一份统一任务数据，让看板、四象限和日历成为同一任务的三个投影视图：

- 看板回答“任务处于什么执行阶段”。
- 四象限回答“任务的重要性与紧急性是什么”。
- 日历回答“任务安排在什么日期”。
- 标签和协作人是任务的全局字段，由三个模块共同使用。
- 任意模块修改任务，其他模块读取到的是同一条任务记录。
- 全局“任务视图联动”默认开启；开关只控制任务是否依据字段自动加入其他视图，不创建独立副本，也不关闭数据一致性。

该功能有明确价值，应作为任务领域模型统一工程实施，而不是在现有 `tasks` 与 `kanban_cards` 之间增加事件监听。

## 2. 当前状态与主要问题

当前实现存在两套任务实体：

1. 四象限使用 `tasks`、`MatrixTask`、`useTasks` 和任务命令。
2. 看板使用 `kanban_cards`、`KanbanCard`、`useKanban` 和独立看板命令。
3. 看板另有可自定义的 `kanban_priorities`、`kanban_tags`、`kanban_collaborators`。
4. 日历主要渲染 `events`；任务只有一对一的 `linkedEventId`，有截止日期的任务不会自然成为日历项目。
5. `App` 同时挂载 `useTasks` 与看板内部的 `useKanban`，跨模块写入后无法依靠一个共享状态源立即刷新。

如果继续在两套实体间做同步，会出现重复任务、删除冲突、修改覆盖、开关关闭后的数据分叉以及难以恢复的部分成功。因此必须先统一数据模型，再统一交互。

## 3. 目标与非目标

### 3.1 目标

1. 一条任务在数据库中只有一份主记录和一个稳定 ID。
2. 全局优先分类仅保留四个固定值，并允许“未分类”状态。
3. 有优先分类的任务可显示在四象限；有截止日期的任务可显示在日历；所有进入看板的任务拥有泳道和顺序。
4. 标签与协作人改为应用级全局资源，并可在三个模块中编辑和筛选。
5. 三个模块均提供设置入口，但入口指向同一套全局字段管理能力。
6. 联动开关默认开启，关闭和重新开启均不复制、删除或覆盖任务内容。
7. 完整迁移当前四象限任务、看板卡片、标签、协作人、泳道和任务—日程关联。
8. 保持 Nowly 的 local-first、离线可用和单机 SQLite 事务语义。

### 3.2 非目标

首期不包含：

- 多工作区、多组织或多看板。
- 登录账号、真实成员邀请、权限控制和实时协作。
- 评论、附件、子任务、依赖关系和活动时间线。
- 将任务日期自动复制成 `events`。
- 根据截止日期自动修改“紧急”属性。
- 自定义第五种优先级、重命名四象限或自定义象限含义。
- 自动按标题合并疑似重复的旧任务。
- 跨设备同步。

当前“协作人”仍是本地保存的人员名称，用于任务归属和筛选，不代表该人员已获得应用访问权限。未来引入工作区后，再将其迁移为工作区成员关系。

## 4. 核心领域模型

### 4.1 统一任务是唯一事实来源

统一后的任务建议使用 `Task` 命名，替代前端的 `MatrixTask` 和 `KanbanCard` 业务实体。看板卡片只是一种 `TaskCard` 展示组件，不再对应独立数据库记录。

```ts
export type TaskPriority =
  | 'important_urgent'
  | 'important_not_urgent'
  | 'not_important_urgent'
  | 'not_important_not_urgent';

export type TaskView = 'kanban' | 'matrix' | 'calendar';

export type Task = {
  id: string;
  title: string;
  description: string;
  priority: TaskPriority | null;
  dueDate: string | null;             // 本地日期 YYYY-MM-DD
  completed: boolean;
  laneId: string;
  boardPosition: number;
  tagIds: string[];
  collaboratorIds: string[];
  linkedEventId: string | null;       // 兼容现有显式任务—日程关联
  createdAt: string;
  updatedAt: string;
};
```

首期保留单个 `dueDate`。日历将任务渲染为对应日期的全天任务项。以后需要时间块时，再独立增加 `scheduledStartAt` / `scheduledEndAt`，不能把截止日期误解释为开始时间。

### 4.2 四种优先分类

固定内部值及显示文案：

| 内部值 | 中文文案 | 含义 |
|---|---|---|
| `important_urgent` | 重要且紧急 | 第一象限 |
| `important_not_urgent` | 重要不紧急 | 第二象限 |
| `not_important_urgent` | 不重要但紧急 | 第三象限 |
| `not_important_not_urgent` | 不重要不紧急 | 第四象限 |

规则：

- `null` 表示未分类，不是第五种优先级。
- 四种值是稳定枚举，不以中文文案存库。
- 四象限名称和语义不可由用户修改。
- 旧四象限的 `quadrant` 直接迁移为新的 `priority`。
- 旧的数字优先级 `1 | 2 | 3` 被移除，不再与四象限形成两套相互冲突的优先概念。
- 系统不会因为逾期或临近日期自动改变优先分类，只可提示用户自行调整。

### 4.3 状态、泳道与完成状态

看板泳道继续保留并可新增、重命名、改色和排序。任务的 `laneId` 与全局 `completed` 必须保持一致：

- 系统保存一个 `completionLaneId`，默认指向稳定 ID 的“已完成”泳道。
- 任务移动到完成泳道时，原子地设置 `completed = true`。
- 任务移出完成泳道时，原子地设置 `completed = false`。
- 在四象限或任务详情中勾选完成时，任务移动到完成泳道末尾。
- 取消完成时，任务移动到默认未完成泳道 `defaultLaneId` 末尾。
- 删除默认泳道或完成泳道前，必须先选择替代泳道；不得留下悬空任务。

泳道是执行状态，优先分类是决策属性，两者互不替代。

### 4.4 标签

标签是应用级全局资源：

```ts
export type TaskTag = {
  id: string;
  name: string;
  color: HexColor;
  archivedAt: string | null;
  createdAt: string;
  updatedAt: string;
};
```

规则：

- 一条任务可关联多个标签。
- 名称修剪后不能为空，并进行大小写不敏感的唯一性校验。
- 修改名称或颜色后，三个视图同步展示新值。
- 默认操作为“归档”，归档标签不再出现在新增选择器，但历史任务仍显示它。
- 永久删除属于二级危险操作，必须显示使用任务数量并清理关联，不删除任务。
- 当前单机产品中的“全局”是整个 Nowly 应用范围；未来增加工作区时补充 `workspace_id`，不改变任务关联方式。

### 4.5 协作人

协作人同样是应用级全局资源：

```ts
export type TaskCollaborator = {
  id: string;
  name: string;
  archivedAt: string | null;
  createdAt: string;
  updatedAt: string;
};
```

规则与标签一致：统一创建、重命名、归档和影响提示。一条任务可有多个协作人。首期不加入头像、邮箱、账号、角色或权限字段。

## 5. 视图投影与联动开关

### 5.1 为什么需要显式视图成员关系

只依靠实时查询条件无法正确表达“关闭联动后保留当前显示状态”。因此增加轻量的视图成员关系：

```text
task_view_memberships
- task_id
- view                kanban | matrix | calendar
- position            四象限手动排序预留；其他视图可为空
- created_at
PRIMARY KEY (task_id, view)
```

它只记录任务出现在哪个视图，不保存标题、日期、标签等业务字段，因此不会形成任务副本。

### 5.2 联动开启，默认状态

`taskViewLinkingEnabled = true` 时，后端在每次任务写事务中自动维护成员关系：

| 条件 | 自动结果 |
|---|---|
| 任意有效任务 | 加入看板；没有泳道时使用默认未完成泳道 |
| `priority != null` | 加入四象限并显示在对应象限 |
| `priority == null` | 从四象限移除 |
| `dueDate != null` | 加入日历并显示在该日期 |
| `dueDate == null` | 从日历移除 |

示例：

- 在看板设置“重要且紧急”，保存事务同时增加四象限成员关系。
- 在四象限给任务设置截止日期，保存事务同时增加日历成员关系。
- 在日历创建任务，任务拥有日期并进入日历，同时进入看板默认泳道；未设置优先分类时不进入四象限。
- 在日历拖动任务，直接更新该任务的 `dueDate`。
- 在四象限跨象限拖动任务，直接更新该任务的 `priority`。
- 在看板跨泳道拖动任务，直接更新 `laneId`、`boardPosition` 和必要的完成状态。

### 5.3 联动关闭

`taskViewLinkingEnabled = false` 时：

1. 关闭瞬间不改变任何成员关系，当前视图分布被“冻结”。
2. 后续修改优先分类或日期，不再自动把任务加入其他视图。
3. 任务详情显示“显示在”复选项，允许手动加入或移出看板、四象限、日历。
4. 加入四象限前必须先设置优先分类；加入日历前必须先设置日期。
5. 清空优先分类时必须移除四象限成员关系；清空日期时必须移除日历成员关系。这是结构校验，不属于自动联动。
6. 不允许移除任务的最后一个视图成员关系，避免任务完全不可发现；未来若提供全局任务中心，可再放宽。
7. 任何视图中对标题、完成、标签、协作人等字段的修改仍作用于同一条任务。

### 5.4 重新开启联动

重新开启时，在一个数据库事务中按照 5.2 的规则重建全部任务的成员关系。设置界面需提示：

> 开启后，任务会重新根据优先分类和日期自动显示在四象限与日历中，并统一加入看板。任务内容不会被修改。

操作失败时设置值和成员关系同时回滚。

### 5.5 开关位置

三个模块的设置弹窗都可显示同一个全局开关，也可在应用设置中显示。所有入口读写同一配置：

```text
任务视图联动 [开启]
根据优先分类、日期和状态在看板、四象限、日历中自动展示同一任务。
```

禁止出现三个彼此独立的“看板联动”“日历联动”“四象限联动”主开关。

## 6. 模块交互设计

### 6.1 共同原则

- 三个模块 Header 均提供设置入口。
- 任务卡片或任务条均可打开同一个 `TaskDialog`。
- 全量字段在统一任务弹窗中编辑；高频字段可在模块内快捷修改。
- 设置入口可以多个，数据管理实现只能有一套。
- 所有新 UI 严格复用 `design.md`：40px 操作按钮、15.2px 圆角、Good Checkbox/Radio、下划线 Tab、Lucide 图标、无动画和无平滑滚动。

### 6.2 统一任务弹窗

统一后的任务弹窗包含：

1. 标题，必填。
2. 描述，选填。
3. 优先分类，四选一并允许清除为“未分类”。
4. 截止日期，选填，复用离线 `DatePicker`。
5. 看板泳道。
6. 完成状态。
7. 标签，多选。
8. 协作人，多选。
9. 显式关联日程，保留现有兼容能力。
10. 联动关闭时显示“显示在”视图选择。

从不同模块打开时可以聚焦对应字段，但字段集合和保存命令必须相同。

### 6.3 看板

Header 设置使用下划线 Tab：

- **视图**：卡片字段显示、筛选、已完成任务显示策略。
- **泳道**：泳道增删改、顺序、默认泳道、完成泳道。
- **任务字段**：管理标签、管理协作人、查看固定优先分类。
- **联动**：全局任务视图联动开关及说明。

看板任务卡可展示优先分类、日期、标签和协作人。设置优先分类或日期后是否自动进入其他视图由全局开关决定。

原“管理字段”中的自定义优先级 CRUD 被移除；优先分类改为只读说明和四个固定选项。

### 6.4 四象限

四象限 Header 增加设置按钮。设置内容：

- 卡片显示字段：截止日期、标签、协作人、泳道状态。
- 筛选：标签、协作人、完成状态。
- 象限内排序：手动、截止日期、创建时间。
- 管理标签、管理协作人的统一入口。
- 全局联动开关。

交互：

- 跨象限拖动更新全局 `priority`。
- 联动开启时，拖入象限可使原本未分类任务自动加入四象限。
- 完成勾选同步看板完成泳道。
- “未分类”不作为第五象限；可在设置中提供未分类任务入口或计数，点击打开筛选列表。

### 6.5 日历

日历同时渲染两类对象，但不混淆实体：

- `CalendarEvent`：有起止时间、重复规则、提醒和订阅来源。
- `Task`：以截止日期显示的全天任务项。

显示要求：

- 任务项必须使用任务图标或“任务”语义，不只依靠颜色与日程区分。
- 点击任务打开统一任务弹窗；点击日程继续打开日程弹窗。
- 月视图拖动任务更新 `dueDate`；日程拖动仍更新事件时间。
- 日期详情分为“日程”和“任务”两个区域。
- 任务完成后按日历设置决定隐藏、弱化或保留。
- 不因 `dueDate` 自动创建 `events`，避免一条事项在同一天重复显示两次。

日历设置增加：

- **基本**：现有周起始日、日期格式、周末显示。
- **任务**：显示任务、完成任务策略、标签/协作人筛选、任务颜色规则。
- **订阅**：保留现有订阅管理。
- **任务字段**：管理标签和协作人。
- **联动**：全局开关。

### 6.6 全局字段管理

将 `KanbanFieldManagerDialog` 重构为模块无关的 `TaskFieldManagerDialog`：

- 标签和协作人管理使用同一个组件、Repository 和数据库表。
- 三个模块设置均可打开该弹窗。
- 弹窗标题和文案不出现“看板专属”。
- 标签颜色复用全局颜色选择器与最近颜色。
- 归档或永久删除前显示受影响任务数量。
- 固定优先分类不提供新增、重命名、删除和排序。

## 7. 数据库设计

以下为目标逻辑结构，迁移实现可通过 SQLite 重建表完成。

### 7.1 `tasks`

```text
id                    TEXT PRIMARY KEY
title                 TEXT NOT NULL
description           TEXT NOT NULL DEFAULT ''
priority              TEXT NULL CHECK (...四个固定值...)
due_date              TEXT NULL
completed             INTEGER NOT NULL CHECK (completed IN (0,1))
lane_id               TEXT NOT NULL REFERENCES task_lanes(id)
board_position        INTEGER NOT NULL
linked_event_id       TEXT NULL REFERENCES events(id) ON DELETE SET NULL
created_at            TEXT NOT NULL
updated_at            TEXT NOT NULL
```

约束与索引：

- 标题修剪后不能为空。
- 日期必须是有效 `YYYY-MM-DD`。
- `board_position` 在同一泳道内由后端事务稠密重排。
- 索引：`(lane_id, board_position)`、`(priority, completed)`、`(due_date, completed)`、`updated_at`。
- 保留任务与日程当前的一对一显式关联和唯一索引。

### 7.2 `task_lanes`

由 `kanban_lanes` 演进而来，保留 ID、名称、颜色、位置和时间戳。默认泳道与完成泳道由设置保存稳定 ID，不依赖可修改名称判断语义。

### 7.3 `task_tags` / `task_collaborators`

由当前看板全局字段演进而来，新增 `archived_at`。关系表改为：

```text
task_tag_links(task_id, tag_id, PRIMARY KEY(task_id, tag_id))
task_collaborator_links(task_id, collaborator_id, PRIMARY KEY(task_id, collaborator_id))
```

删除任务级联删除关系；归档字段不删除关系；永久删除字段只级联关系，不删除任务。

### 7.4 `task_view_memberships`

```text
task_id      TEXT NOT NULL REFERENCES tasks(id) ON DELETE CASCADE
view         TEXT NOT NULL CHECK (view IN ('kanban','matrix','calendar'))
position     INTEGER NULL
created_at   TEXT NOT NULL
PRIMARY KEY (task_id, view)
```

索引：`(view, position, task_id)`。

### 7.5 设置

新增设置：

```text
task_view_linking_enabled = true
default_task_lane_id      = "kanban-lane-todo"
completion_task_lane_id   = "kanban-lane-done"
task_view_preferences     = { calendar: {...}, matrix: {...}, kanban: {...} }
```

前两个泳道设置必须在写入时校验对应泳道存在。视图筛选与字段显示是视图级配置，不是任务数据。

## 8. 历史数据迁移

计划使用下一个可用数据库迁移版本；以当前仓库为基线应为 migration 18。实施前必须再次确认版本号，禁止重排或改写已发布迁移。

### 8.1 迁移前保护

- 首次执行不可逆结构迁移前，复制数据库为带版本号的备份文件。
- 备份失败则不执行迁移，并向用户显示可恢复错误。
- SQL 数据搬迁在一个 `IMMEDIATE` 事务中执行。
- 提交前运行 `PRAGMA foreign_key_check` 和数量校验。
- 记录迁移审计：旧四象限任务数、旧看板卡片数、新任务数、标签数、协作人数、无法直接映射的优先级数。

### 8.2 四象限任务迁移

每条旧 `tasks`：

- 保留原 ID、标题、截止日期、完成状态、日程关联、创建与更新时间。
- `note` 迁移到 `description`。
- `quadrant` 迁移到新的四值 `priority`。
- 旧数字 `priority` 不再作为业务字段；按旧排序结果初始化四象限 `position`，避免无理由打乱用户列表。
- 已完成任务分配至完成泳道，未完成任务分配至默认未完成泳道。
- 初始加入四象限成员关系。

### 8.3 看板卡片迁移

每条旧 `kanban_cards`：

- 保留原 ID；若与旧 `tasks` 极小概率冲突，则给看板 ID 加稳定前缀并在审计表记录映射。
- 保留标题、描述、截止日期、泳道和泳道内顺序。
- 保留标签和协作人关系。
- 默认加入看板成员关系。
- 位于稳定 ID 的默认完成泳道中的任务设置为完成；其他泳道任务保持未完成。自定义泳道不通过名称猜测完成语义。

### 8.4 旧看板自定义优先级迁移

全局优先分类最终只能是四个固定值，因此采用保守映射：

1. 名称规范化后精确匹配四个中文名称、四个内部值或批准的英文全称时，映射到对应固定优先分类。
2. “高/中/低”“P0/P1/P2”等无法可靠判断重要性与紧急性的值不得猜测。
3. 无法映射的优先级转换为标签 `旧优先级：{原名称}`，保留原颜色，并关联到原任务。
4. 若生成标签与已有标签重名，按规范化名称合并并复用已有标签。
5. 迁移审计记录转换数量，迁移后首次进入任务字段管理时可显示一次说明。

这样既满足新的四分类约束，又不静默丢失旧优先级信息。

### 8.5 重复任务

旧四象限任务与旧看板卡片没有可靠关联 ID。即使标题、日期完全相同，也不得自动合并，否则可能误删用户有意创建的不同任务。全部迁移为独立任务；后续可提供人工合并工具，但不属于首期。

### 8.6 初始联动协调

迁移完成后默认联动为开启，并在同一事务中执行一次成员关系协调：

- 所有任务加入看板。
- 有固定优先分类的任务加入四象限。
- 有截止日期的任务加入日历。

因此升级后旧四象限任务会出现在看板，旧看板有日期的任务会出现在日历；这是本功能的预期结果，需要在版本说明中明确告知。

### 8.7 旧表处置与回滚

- 数据复制和校验成功后再删除旧 `kanban_cards`、旧关系表和自定义优先级表。
- 不提供向下迁移；用户需要降级时必须关闭应用并恢复迁移前数据库备份。
- 新版本第一次稳定发布后仍保留迁移审计，不包含用户隐私外传。

## 9. Repository、命令与状态管理

### 9.1 统一 Repository 契约

新增领域级接口，逐步替代 `listTasks` 与看板卡片 CRUD：

```ts
export type TaskWorkspaceSnapshot = {
  tasks: Task[];
  lanes: TaskLane[];
  tags: TaskTag[];
  collaborators: TaskCollaborator[];
  linkingEnabled: boolean;
  viewPreferences: TaskViewPreferences;
};

getTaskWorkspaceSnapshot(): Promise<TaskWorkspaceSnapshot>;
createTask(originView: TaskView, draft: TaskDraft): Promise<Task>;
updateTask(id: string, draft: TaskDraft): Promise<Task>;
deleteTask(id: string): Promise<void>;
setTaskCompleted(id: string, completed: boolean): Promise<Task>;
moveTaskToLane(id: string, laneId: string, targetIndex: number): Promise<Task>;
moveTaskToPriority(id: string, priority: TaskPriority): Promise<Task>;
moveTaskToDate(id: string, dueDate: string): Promise<Task>;
setTaskViewMemberships(id: string, views: TaskView[]): Promise<Task>;
setTaskViewLinking(enabled: boolean): Promise<TaskWorkspaceSnapshot>;
```

标签、协作人和泳道命令改为 `Task*` 命名。所有复杂写入必须在 Rust 后端单事务完成，前端不得用多次 IPC 拼接事务。

### 9.2 单一前端状态源

在应用层建立 `TaskWorkspaceProvider` / `useTaskWorkspace`：

- `App` 只加载一次任务工作区快照。
- 看板、四象限、日历通过 selector 读取同一快照。
- 所有任务写操作由该 Provider 统一执行、更新和报错。
- 删除 `useTasks` 与 `useKanban` 对任务分别加载的长期状态；迁移阶段可保留兼容适配器，但不得继续作为两个事实来源。
- 标签或协作人被修改后，不需要三个模块各自重新请求。
- 拖放可乐观更新；失败恢复操作前快照并显示静态错误，不使用动画。
- 同一任务保存期间禁用冲突操作；不同任务可并行提交。

### 9.3 后端事务边界

以下操作必须原子化：

- 更新任务字段并协调自动视图成员关系。
- 任务跨泳道移动、源/目标泳道重排和完成状态更新。
- 完成/取消完成和泳道移动。
- 开启联动并重建全部成员关系。
- 删除或替换默认/完成泳道。
- 标签或协作人永久删除及关系清理。
- 任务与日程重新关联。

返回错误继续使用现有 `CommandError`，字段名使用 camelCase 对齐前端。

### 9.4 日程边界

`events` 保持独立领域：

- 日历加载事件仍使用范围查询。
- 日历任务来自统一任务快照或独立范围查询，不从事件表反推。
- `linkedEventId` 只表示用户显式关联，不决定任务是否显示在日历。
- 删除任务不删除关联日程；删除日程只清空任务关联，沿用当前规则。

## 10. 分阶段实施顺序

### 阶段 0：保护与契约测试

- 为现有两套数据建立迁移夹具。

- 冻结统一枚举、字段命名和开关语义。

退出条件：迁移测试先失败并准确描述目标行为。

### 阶段 1：数据库与 Rust 领域层

- 增加目标表、设置和迁移逻辑。
- 实现统一 Task 模型、快照和事务命令。
- 实现视图成员协调器，所有写命令复用同一函数。
- 保留旧 IPC 的临时适配器，确保尚未迁移的前端仍能编译；适配器不得写旧表。

退出条件：Rust 单元测试覆盖创建、更新、移动、完成、联动开关和历史迁移。

### 阶段 2：前端统一状态与任务弹窗

- 更新 Repository 类型和 Tauri 实现。
- 建立 `TaskWorkspaceProvider`。
- 将 `TaskModal` 与 `KanbanTaskDialog` 合并为统一任务弹窗。
- 将标签/协作人选择接入全局数据。

退出条件：任一入口编辑任务后，共享快照立即反映完整字段。

### 阶段 3：看板与四象限切换

- 看板改为渲染统一任务，保留泳道拖放能力。
- 四象限改为按固定优先分类投影。

### 阶段 4：日历任务投影

### 阶段 5：设置与全局字段管理

退出条件：多个设置入口修改的是同一开关、标签和协作人数据。

### 阶段 6：清理与发布验证

- 移除旧前端模型、Hook、IPC 适配器和无引用文案。
- 更新旧看板规格和用户文档中的独立任务描述。
- 执行完整 Rust、Vitest、TypeScript、Vite 和 Playwright 门禁。
- 在真实升级数据库副本上做人工验收。

退出条件：仓库不存在对旧 `kanban_cards` 业务实体的运行时依赖。

## 12. 验收标准

满足以下条件才可宣布完成：

- [ ] 数据库中不存在两套可独立编辑的任务主记录。
- [ ] 全局优先分类只有四个固定值，允许未分类。
- [ ] 看板、四象限、日历编辑的是同一任务 ID。
- [ ] 联动开启时，优先分类和日期可正确驱动视图出现与移除。
- [ ] 联动关闭时，跨视图自动加入停止，但已有任务数据仍一致。
- [ ] 重新开启联动不丢失标题、日期、标签、协作人、泳道或关联日程。
- [ ] 标签和协作人只有一套全局资源，三个模块均可进入统一管理。
- [ ] 日历中的任务与日程在视觉和可访问语义上可区分。
- [ ] 完成状态与完成泳道始终一致。
- [ ] 旧自定义优先级没有静默丢失。
- [ ] 迁移失败可回滚并保留原数据库备份。
- [ ] 所有自动化门禁通过，且没有新增动画、过渡或设计 Token 例外。

## 13. 风险与控制

| 风险 | 等级 | 控制措施 |
|---|---|---|
| 两套任务合并导致数据丢失 | 高 | 迁移前备份、数量守恒、单事务、审计记录、禁止标题自动去重 |
| 自定义优先级无法映射四象限 | 高 | 仅精确映射，其他转“旧优先级”标签 |
| 三模块各自缓存导致界面陈旧 | 高 | 单一 `TaskWorkspaceProvider`，禁止双 Hook 事实来源 |
| 看板完成泳道与完成状态冲突 | 中 | 稳定完成泳道设置，后端原子协调 |
| 关闭联动后任务不可发现 | 中 | 冻结成员关系、禁止移除最后一个视图、结构字段校验 |
| 日历任务与日程重复 | 中 | 不自动创建 Event，使用不同实体类型和视觉语义 |
| 协作人被误解为真实共享 | 中 | UI 明确“本地协作人”，首期不承诺权限与通知 |
| 一次性改动过大 | 高 | 按领域层、状态层、视图层分阶段，每阶段保留可验证退出条件 |

## 14. 最终决策清单

1. 采用统一 Task 模型，不做任务副本同步。
2. 四象限就是全局优先分类，删除旧数字优先级和看板自定义优先级概念。
3. 允许未分类，但未分类不显示为第五象限。
4. 看板状态、四象限优先分类、日历日期是三个独立维度。
5. 标签和协作人为应用级全局字段；管理入口集中，模块入口可重复。
6. 全局联动默认开启；关闭只冻结自动投影，不分叉数据。
7. 使用 `task_view_memberships` 表达关闭联动后的可见范围。
8. 日历直接渲染任务，不把任务复制成日程。
9. 旧不可映射优先级转标签，不猜测、不丢弃。
10. 先迁移数据和 Repository，再迁移 UI；禁止先在前端用监听器拼接同步。
